This guide demonstrates a multi-server setup using pub/sub for horizontal scaling. Multiple server instances share a pub/sub backend to synchronize document updates across nodes.

## What it demonstrates

In a typical websocket-only setup, each client is connected via the websocket to a single server. But, what happens if you have two clients who access the same document?
In a multi-node setup, it is possible for one client to be connected to one server and the other client to be connected to another server. This can lead to inconsistent state and conflicts, since the system is operating in a sort of split-brain scenario.

This example demonstrates how each server instance can coordinate with each other over a pub/sub interface to ensure that all clients see the same state. Specifically achieving the following:

- Each server instance has a unique `nodeId`
- Messages are published to PubSub topics
- Each server filters out its own messages
- Document updates are replicated across all server instances

## Server Setup

```typescript
import { Server } from "teleportal/server";
import { RedisPubSub } from "teleportal/transports/redis";
import { UnstorageDocumentStorage } from "teleportal/storage";

const server = new Server({
  storage: async (ctx) => {
    // Shared storage backend
    return new UnstorageDocumentStorage(storage, {
      keyPrefix: "doc",
      encrypted: ctx.encrypted,
    });
  },
  pubSub: new RedisPubSub({
    path: "redis://localhost:6379",
  }),
  nodeId: process.env.NODE_ID || `node-${uuidv4()}`,
});
```

## Running Multiple Instances

```bash
# Instance 1
NODE_ID=node-1 PORT=3000 node server.js

# Instance 2
NODE_ID=node-2 PORT=3001 node server.js

# Instance 3
NODE_ID=node-3 PORT=3002 node server.js
```

## How It Works

Anytime that a document update (or other broadcast message) is applied to a server, the server will publish that message to the PubSub topic to broadcast to all other servers that may be listening. Each server will then apply/broadcast that message to its own clients.

In this example, we are using Redis as the PubSub backend, but you can use any PubSub backend that implements the PubSub interface (literally publish/subscribe with callbacks).

## Durability

Plain pub/sub is fire-and-forget: a node that briefly disconnects silently misses the messages published during the gap. It keeps serving its connected clients stale state until they happen to reconnect. Storage still has every update (the session holds no in-memory Y.Doc), so this is **staleness, not data loss** — but it's still a hole.

Durability closes it as an **optional capability of the `PubSub` interface**. The base contract stays as simple as ever (a custom backend only needs `publish`/`subscribe`); a durable backend additionally implements `DurablePubSub` (`durable: true`). The shipped backends are durable:

- **`InMemoryPubSub`** and **`RedisPubSub`** are durable out of the box (Redis via Streams — no new dependency).
- **`NatsJetStreamPubSub`** (`teleportal/transports/nats/jetstream`) is durable via JetStream. Core-NATS `NatsPubSub` is unchanged and stays fire-and-forget.

How it works:

- **Per-message classification.** Each message declares `durability: "durable" | "ephemeral"`. Document updates and full-state sync are durable (persisted, replayed after a blip); awareness, acks, the sync handshake, and presence RPC pushes are ephemeral (they self-heal, so they ride a non-persistent channel and don't consume retention). This is automatic — you never tag publishes by hand.
- **Transparent catch-up.** After a reconnect, a durable backend resumes from its last-read position and delivers everything missed, in order. The server core never touches offsets.
- **Beyond-retention gaps.** If a node is disconnected long enough that its resume position is trimmed out of retention, the backend reports a gap and the session heals by pushing a storage-derived full-state `sync-step-2` to its local clients (a `"replication-gap"` session event fires too). This heals when **storage is shared across nodes** (the standard deployment); with per-node storage, only in-retention durable replay heals cross-node gaps.

Retention is tunable per backend (`stream.maxLen`/`ttlMs` for Redis, `maxMsgsPerSubject`/`maxAgeMs` for JetStream). To opt out entirely and keep pure fire-and-forget, set `isDurableTopic: () => false`.

:::note[Replay and custom RPC]
Replayed document updates and sync messages are CRDT-idempotent and de-duplicated, so replay is safe. RPC is never fanned out over pub/sub, so it is unaffected. If you add a custom cross-node publish path with side effects, keep those handlers idempotent.
:::
